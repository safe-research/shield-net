## Claim

`decode_multi_send` builds one `SafeTransaction` per packed sub-call and fills seven of its twelve
fields with zeros: `chain_id`, `safe_tx_gas`, `base_gas`, `gas_price`, `gas_token`, `refund_receiver`
and `nonce`. Only `safe`, `to`, `value`, `data` and `operation` carry real values.

This is the same defect that F-ENG-032 documents in `RefundChecker` — a synthetic `SafeTransaction`
whose `chain_id` is zero, handed to a checker that gates on `chain_id` and therefore always abstains.
There the fields are zeroed by `..Default::default`; here they are written out explicitly. The
difference is that `RefundChecker`'s consumer is fixed and known, so the bug is live, while
`decode_multi_send`'s output goes to a `pub fn` (`sub_transactions`) that any checker may call.

Today no consumer is broken. All three call sites read the *outer* transaction's `chain_id` and pass
that down — `StakingChecker` gates at `staking.rs:89` before decoding, `CowChecker` passes
`transaction.chain_id` explicitly at `cow.rs:437`, and `BaseChecker`'s `check_multi_send` reads only
`to`, `value`, `data` and `operation`. `AddressPoisoningChecker`, the one checker that would silently
abstain on a zeroed `chain_id`, is never given a sub-transaction: `main.rs:52-73` runs it on the
top-level transaction only.

So this is a trap, not a live bug — and it is a trap that has already been walked into once, in the same
crate, in the same release. The next checker that calls `sub_transactions` and reads `chain_id` (to
select a chain-specific address table, as `CowChecker` and `StakingChecker` both do), or reads
`refund_receiver` (the field F-ENG-031 says nobody reads), gets a zero and either abstains silently or
concludes the sub-call has no refund leg. Neither failure produces a log line.

`chain_id`, `safe_tx_gas`, `base_gas`, `gas_price`, `gas_token`, `refund_receiver` and `nonce` have no
per-sub-call meaning in the MultiSend wire format — the packed entry carries only
`operation`/`to`/`value`/`dataLength`/`data`. But `chain_id`, `nonce`, and the four refund fields *do*
have a well-defined value for every sub-call: the outer transaction's, which is in scope at
`decode_multi_send_call` (`tx.chain_id`, `tx.nonce`, …) and is already being used for `safe`
(`decode_multi_send(tx.safe, …)`, `:160`). Propagating `safe` and not the rest is the inconsistency.

## Trigger

None today — this is a latent defect, and the finding says so. The concrete way it becomes live is the
remediation already proposed for a Critical finding in this crate: F-ENG-035 (`BlocklistChecker` sees
only the top-level `to`) names `sub_transactions` as the helper its fix would use, and F-ENG-031's fix
requires reading `refund_receiver`/`gas_price`. A blocklist or refund check written over
`sub_transactions` output reads `Address::ZERO` for `refund_receiver` on every sub-call and would
conclude, wrongly and silently, that no sub-call has a refund leg. The zero address is also a plausible
blocklist entry, which would turn the same zeroing into a false *denial*.

## Considered and rejected

- **"The zeroed fields are meaningless for a sub-call, so zero is the honest value."** True for
  `safe_tx_gas`, `base_gas` and `nonce`, which are properties of the enclosing `execTransaction`. Not
  true for `chain_id`, which is a property of the chain and identical for every sub-call, and the code
  already accepts that argument for `safe`, propagating it explicitly.
- **"`Default::default` would be equivalent, so this is stylistic."** The point is the opposite: it is
  equivalent, and `..Default::default` in `refund.rs:105-117` is exactly what F-ENG-032 documents as a
  live Critical-severity bug. The same value in the same crate, produced deliberately rather than by
  omission, is worth one line of defence.
- **"No current consumer reads these fields, so there is no finding."** Recorded honestly as the reason
  this is Low and not Medium. An absence that is safe only because of who happens to call it, in a
  module whose callers are being extended by two open findings' remediations, is worth writing down.
- **"This duplicates F-ENG-032."** Same defect class, different site, and F-ENG-032 stays canonical for
  the live instance. F-ENG-032's Location is `checkers/refund.rs` and its claim is specific to
  `RefundChecker`'s delegated call; neither it nor any other finding cites
  `multi_send.rs:116-129`.

## Remediation options

1. **Propagate the outer values.** Pass `tx` rather than `tx.safe` into `decode_multi_send` and set
   `chain_id: tx.chain_id`, `nonce: tx.nonce`, and the four refund fields from `tx`. Sub-calls then
   describe themselves accurately and any future checker reads real values. Tradeoff: a checker that
   sums refund exposure across sub-calls would now double-count the single outer refund leg — so pair
   this with option 2.
2. **Make the shape un-mistakable.** Return a distinct type (`SubCall { to, value, data, operation }`)
   instead of a `SafeTransaction`, so a checker cannot read a field that has no per-sub-call meaning.
   This is the fix that removes the class rather than the instance. Tradeoff: the existing checkers'
   helpers take `&SafeTransaction` and would need adapting — about a dozen call sites in
   `staking.rs`, `cow.rs` and `base.rs`.
3. **Document it at the call site.** A `// NOTE: chain_id/nonce/refund fields are not populated —` comment
   on `sub_transactions` is the zero-cost floor. It does not stop the next mistake, only shortens the
   time to find it.

Tests to add: a `decode_multi_send` assertion pinning which fields are populated and which are not, so
the choice is deliberate and any change to it is visible; and, if option 1 is taken, a test that a
sub-call's `chain_id` equals the outer transaction's. `multi_send.rs` currently has **0** tests in file
(`state/baseline.md` §5). No code is committed.

### 2. Second site, or the same site by another route? — **A genuine second site.**

F-ENG-032's defect is at `checkers/refund.rs:105-117`, in `refund_transfer`, reached by
`..Default::default`. This is `contracts/multi_send.rs:116-129`, in `decode_multi_send`, written out
explicitly. Different function, different file, different consumer, different fix. They are the same *class* —
a synthesised `SafeTransaction` that silently loses fields a checker may gate on — at two sites.

What *is* duplicated is my own F-ENG-032 §3 note, which describes this site rather than F-ENG-032's. That note
and this file are one thing said twice, and this file says it better: it has a full template, an enumerated
consumer analysis and a remediation. See §5 for the canonical assignment.

### 3. Latent or live? — **Latent. Confirmed by exhaustive enumeration, not by sampling.**

I enumerated every non-test consumer of both entry points rather than checking the three the file names:

| Consumer | Reads a zeroed field on a sub-call? |
| --- | --- |
| `checkers/staking.rs:93` | No — gates on the **outer** `chain_id` at `:89`; the helpers at `:157`, `:168`, `:179` read only `operation`, `value`, `to`, `data`. |
| `checkers/cow.rs:429` | No — gates on the outer `chain_id` at `:422-427` and passes `transaction.chain_id` explicitly into `check_presignature_batch` at `:437`. |
| `checkers/base.rs:206` (`check_multi_send`) | No — `check_calls`/`check_delegate_calls` read only `operation`, `safe`, `to`, `data`. |
| `contracts/target_effects.rs:47` | No — `decode_call` reads only `value`, `to`, `data`. |
| `checkers/address_poisoning.rs` | Never receives a sub-call at all — `main.rs:72` registers it against the top-level transaction only. |

So no live impact today, and the file is right to say so plainly rather than inflate it. I also confirm the
detail that makes the current consumers safe and which the file does not call out: **`value` is *not* zeroed**
(`multi_send.rs:120`), which is what keeps `staking.rs`'s and `cow.rs`'s `!tx.value.is_zero` guards meaningful
on sub-calls. Had `value` been zeroed too, this would be live today and Critical.

### 4. Does it interact with F-ENG-044 (the first-non-abstain-wins root cause) or F-ENG-031? — **No, and this is worth stating precisely.**

No checker returns a verdict *about a sub-transaction*. `StakingChecker` and `CowChecker` consume sub-calls as
evidence and return a verdict about the **outer** transaction. So there is no path where a checker affirms on a
synthesised sub-transaction whose refund fields were zeroed away, and this defect neither causes nor deepens
F-ENG-031: that finding's cause is that the affirmers never read the **outer** transaction's refund fields, which
are fully populated and always were. Removing this defect entirely would not change F-ENG-031, and vice versa.
The two are independent, and the report should not present this as a contributing cause of the Criticals.

**Scope correction that follows from the same reasoning.** The file's strongest argument — "these fields have a
well-defined value for every sub-call: the outer transaction's" — holds for `chain_id` and is genuinely wrong
today. It does **not** hold for the four refund fields or `nonce`: a MultiSend sub-call has no refund leg and no
nonce of its own, because refund and nonce are properties of the enclosing `execTransaction`. Propagating the
outer `gas_price`/`refund_receiver` onto each sub-call would make five sub-calls look like five separate refunds
and would be a worse bug than the zeroing. The file half-concedes this in its "Considered and rejected"; the
finding should be **scoped to `chain_id`** (and the fix limited to it), with the refund fields and `nonce`
documented as deliberately not-applicable rather than propagated. That sharpening is the main thing my review
adds.

### 5. Standalone finding or cross-reference? — **Standalone. Canonical: this file.**

Keep it. It has its own fix site in a file no F-ENG finding touches, and folding it into F-ENG-032 would hide it
from whoever edits `contracts/multi_send.rs`. Canonical assignment:

- **F-XC-052 (this file) canonical** for the `contracts/multi_send.rs:116-129` synthesis site.
- **F-ENG-032 canonical** for the `checkers/refund.rs:105-117` site and for the live impact (a dead
  `RefundChecker`).
- My hazard note at **F-ENG-032 §3 is superseded by this file** and should be read as a pointer to it, not as a
  separate item. Nothing merged, nothing deleted.

The cross-cutting observation both files support, and the reason this is worth keeping at all: the codebase
synthesises `SafeTransaction`s in three places (`refund.rs:105`, `multi_send.rs:116`, and the test helper at
`base.rs:234`) and has no constructor or invariant preventing a synthesised transaction from carrying a
`chain_id` no real transaction could have. A `debug_assert`, a distinct `SubCall` type, or simply refusing
`chain_id == 0` in `AddressPoisoningChecker` would close the class rather than the two instances.

### 6. Finding verdict

**Confirmed** as a latent defect — mechanism verified by direct code reading, latency verified by enumerating
every consumer, and the file is honest that no trigger exists today.

**Certainty 85%**, raised from the drafter's 62%. The self-score is too low: nothing here rests on inference,
the code claims are trivially checkable, and the one soft claim (row 7) is not load-bearing. The gap to the 88-89
ceiling reflects only that `E1` is unreachable this run.

**Severity Low**, confirmed. Not Informational: `chain_id` is a real wrong value, not a documentation or
hardening gap, and it is a concrete trap for the remediation of two confirmed findings (F-ENG-031, F-ENG-035).
Not Medium: §8's Medium requires "incorrect behaviour under unusual but reachable conditions", and this is not
reachable at all today. **Low** — "robustness weaknesses with limited impact" — is the honest band.

**PoC written:** `rust-audit/poc/F-XC-052/` — a `mod tests` block for
`crates/sentinel-engine/src/contracts/multi_send.rs`, which currently has **zero** tests

**What would be run and what it would show.**
`cargo test -p sentinel-engine multi_send::tests::qa_xc_052`. An outer transaction with
`chain_id = 100` (Gnosis, A10) delegatecalling a canonical MultiSend produces a sub-call with
`chain_id = 0`; the test pins that, pins the five other zeroed fields, and pins the fields that
are **not** zeroed — `value` above all, since `multi_send.rs:120` propagating it is what keeps
`staking.rs`'s and `cow.rs`'s `!tx.value.is_zero` guards meaningful on sub-calls, and is why
this is Low rather than Critical. It also covers the `V150Plus` self-call resolution and a
truncated blob, because a file with no tests at all should not gain exactly one.

**Remediation check — option 1 is UNSOUND as written, and this is the main thing this section
adds.** "Pass `tx` rather than `tx.safe` into `decode_multi_send` and set `chain_id: tx.chain_id`,
`nonce: tx.nonce`, and the four refund fields from `tx`" is right for `chain_id` and **wrong for
the other five**. A MultiSend sub-call has no refund leg and no nonce of its own — both are
properties of the enclosing `execTransaction` — so propagating the outer `gas_price` /
`safe_tx_gas` / `base_gas` / `gas_token` / `refund_receiver` would make five sub-calls look like
five separate refunds, which is a worse defect than the zeroing and points a future
refund-summing check in exactly the wrong direction. This is C-ENG-B's scope correction, and it
must be carried into the fix, not just into the finding text: **take the `chain_id` half only**
and document the rest as deliberately not-applicable.

Option 2 (a distinct `SubCall { to, value, data, operation }` type) is sound and removes the
class rather than the instance; its cost — about a dozen call sites in `staking.rs`, `cow.rs` and
`base.rs` that take `&SafeTransaction` — is accurately stated, and if the team will pay it, it
makes option 1 unnecessary. Option 3 (a comment) is the honest zero-cost floor.

**A fourth option neither file lists, and the cheapest defence in depth:** have
`AddressPoisoningChecker` treat `chain_id == 0` as a malformed input rather than as a mismatch to
abstain on (`crates/sentinel-engine/src/checkers/address_poisoning.rs:311-319`). No real
transaction has `chain_id == 0`, so the only thing reaching that branch is a synthesised one —
which is precisely the bug in both `F-ENG-032` and this finding. It does not fix the synthesis,
but it converts a silent dead checker into a `warn!` line and, with `F-XC-010`'s counter, into a
metric.

**Certainty: unchanged at 85%.** No new evidence of my own; the gap to the ceiling is the
unreachable `E1`, as C-ENG-B says.
