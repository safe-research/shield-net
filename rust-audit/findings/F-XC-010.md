## Claim

The sentinel engine starts a Prometheus listener and logs `"serving prometheus metrics and health
endpoint"`, but the crate defines **no metrics of its own**. It has no `metrics.rs`, and it does not
take the `metrics` dependency at all — unlike the validator and the sentinel, which each maintain a
~130-line metrics module. What that endpoint actually serves for this process is `safenet-core`'s
generic JSON-RPC counters (recorded by the provider's observability layer) plus the `tokio` runtime
gauges. Nothing counts a check, a verdict, a checker outcome, or a checker failure.

The consequence is that the engine's *only* stated job is unmeasured. An operator cannot answer,
from metrics:

- how many security checks the engine served, or what the verdict mix was;
- whether any given checker ever produced a non-`Abstain` verdict;
- whether a checker is failing — the difference between "this checker examined the transaction and
  had no opinion" and "this checker could not run at all" is exactly the distinction
  `docs/sentinel-engine.md:25` insists on ("An `abstain` response is successful and deliberate. It
  must not be interpreted as either a secure or insecure transaction"), and nothing measures it;
- whether the CoW or RPC dependencies are erroring.

The per-checker verdict *is* recorded, but only at `trace` (`engine/mod.rs:65`, `:70`), which the
shipped `log_filter = "info"` suppresses in all three sample configs. So at the default
configuration the engine emits no signal at all about what it decided.

This is the finding that makes several others undetectable in production rather than merely
present. `F-XC-005` (this Critic, Confirmed): the shipped sample's single-call 50,000-block
lookback turns every address-poisoning check into an `Abstain` on any provider error, and the only
evidence is one `warn!` line per request. `F-ENG-032` (Confirmed): `RefundChecker` is dead code
because its synthetic transaction carries `chain_id = 0`, so it abstains on every transaction
forever — a checker that has *never once* produced a verdict, which a single counter would have
made obvious on the first day of operation. `F-ENG-005`: an outbound call with no timeout. In each
case a per-checker outcome counter converts a silent, indefinite degradation into a dashboard line
that goes flat.

The remediation is unusually cheap because the label already exists and is already the right shape:
`Checker::name(&self) -> &'static str` (`checkers/mod.rs:26-27`) is a closed set of `&'static str`,
which is exactly what `safenet-core`'s existing metrics convention uses (every label in the three
metrics modules is a `&'static str` from a closed enum), so a checker-outcome counter introduces no
cardinality risk.

## Trigger

No adversary is required; the trigger is any degradation of the checker chain, and two Confirmed
ones already exist in this audit:

1. **Present in the shipped code today.** `F-ENG-032`: `RefundChecker` delegates to
   `AddressPoisoningChecker` with a synthetic transaction built by `..Default::default`
   (`checkers/refund.rs:104-117`), so `chain_id = 0` and the chain-id guard at
   `address_poisoning.rs:312-320` abstains every time. This checker has produced zero verdicts
   since it was written. A `checker_outcomes_total{checker="refund", outcome=...}` counter would
   have shown a checker with no non-abstain outcomes at all, which is the signature of dead code.
2. **Present in the shipped sample configuration.** `F-XC-005`: with
   `address_poisoning_max_block_range` unset, a single `eth_getLogs` covers the whole 50,000-block
   lookback and any error from it — including the rate limiting A4 puts explicitly in scope — is a
   hard `Abstain` with no partial-scan fallback. An operator watching the engine sees 200s, normal
   latency, and no counter moving in the wrong direction.

In both cases the engine keeps answering successfully, the sentinel keeps voting or abstaining, and
the deployment's security posture is quietly lower than the operator believes.

## Considered and rejected

- **"The endpoint is empty, so this is a missing-feature request, not a finding."** It is not
  empty: `observability::init` installs the recorder, `crate::metrics::initialize` registers
  core's metrics, and the engine's own `Provider` records `safenet_core_rpc_requests_total` through
  the observability layer. So an operator scraping the engine gets a populated endpoint that looks
  healthy while telling them nothing about the checker chain — which is worse than an obviously
  empty one, and is why this is filed rather than left as a wish.
- **"Under A3 the engine is an internal component, so observability is the operator's problem."**
  A3 constrains who can *reach* the API; it says nothing about whether the operator can tell that
  the component is working. The two Confirmed findings above are both cases where the engine
  returns HTTP 200 for a check it did not really perform, so the API contract itself cannot carry
  the signal.
- **"The `warn!` lines are sufficient."** They are the current mechanism and they are per-request,
  unaggregated and unlabelled. `address_poisoning.rs:369-378` fires once per affected request; at
  any real request rate that is either noise or nothing, and no alert can be built on it without a
  log-aggregation pipeline the handbooks do not describe. The sibling services did not consider
  their own `warn!` lines sufficient, which is why they have metrics modules.
- **"This is really `F-ENG-009`'s missing startup log."** It is adjacent but distinct.
  `F-ENG-009` says the engine never echoes its resolved configuration at startup, which is a
  one-shot boot-time signal. This is about continuous runtime signal, and neither fixes the other:
  logging `address_poisoning_max_block_range = None` at boot would not reveal that the resulting
  call is failing on every request.
- **Not claimed:** that any specific metric is required by an SLO, or that adding metrics would
  have prevented any defect. The claim is that the engine's own behaviour is unmeasurable, and that
  this is why two Confirmed degradations are silent.
- **Scope.** `crates/sentinel-engine/**` is in scope per PROMPT.md §4, and `Cargo.toml` for the
  crate likewise. `docs/sentinel-engine.md` is cited as reference material only (basis row 11), and
  no finding is filed on it.

## Remediation options

1. Add `crates/sentinel-engine/src/metrics.rs` following the two existing modules exactly. The
   minimum useful set is one counter, `checker_outcomes_total`, labelled by
   `Checker::name` (already `&'static str`, basis row 10) and by outcome — and the outcome label
   must distinguish `secure` / `insecure` / `abstain` / **`error`**, because collapsing the last
   two is precisely the loss this finding is about. Recording it needs one line in
   `SentinelEngine::security_check`'s loop (`engine/mod.rs:63-69`), beside the existing `trace!`.
   Tradeoff: `Checker::check` returns `Verdict`, which has no `Error` variant, so distinguishing
   `abstain` from `error` needs either a richer return type or per-checker recording at the point
   the error is swallowed. The second is uglier but is a strictly local change.
2. Add a second counter for the engine's outbound dependencies — CoW order lookups and the
   address-poisoning `eth_getLogs` — by result. Core already counts RPC requests globally
   (`core/src/metrics.rs:28`), so this is mostly about attributing them to a checker.
3. Cheapest partial measure, if 1 is not wanted now: raise the two verdict lines in
   `engine/mod.rs:65` and `:70` from `trace!` to `debug!`, and document a `log_filter` that
   includes them. This does not give an operator an alertable series, but it removes the situation
   where the default configuration emits nothing.
4. Whatever is chosen, state it in `docs/sentinel-engine.md`'s configuration table, which currently
   documents `observability.metrics_address` as a "Prometheus listener" without saying that the
   reference engine publishes no engine-specific metrics to it.

Tests to add: none meaningful — metric recording is not usefully unit-testable here. The
operational check is a scrape of a running engine asserting that
`sentinel_engine_checker_outcomes_total` is present with one series per configured checker; that
belongs in the devnet script rather than in the crate.

## Trail

- Critic C-XC: **drafted by the Critic**, promoted from R10's coverage log
  (`state/agents/R10.md` §7, observation 2), which reads in full: "**The sentinel-engine exports no
  metrics of its own.** There is no `metrics.rs` in the crate and no `metrics::` call outside
  `safenet-core`, so an operator has no counter for checker outcomes, verdict mix, or CoW/RPC
  failures. This is why F-XC-005's degradation is invisible. Probably R8's to file properly."
  R10 recorded it below the finding threshold and deferred it to R8; R8 did not file it. I checked
  the whole findings directory (`grep -ln "no metrics\|metrics module\|exports no metric"
  rust-audit/findings/*.md`) and no finding covers it as its own claim — `F-ENG-009` mentions the
  absent *startup log*, and `F-ENG-005`/`F-XC-005` mention the absent metrics only in passing as
  a reason their own degradations are invisible. A lead dismissed by deferral to a reviewer who
  did not pick it up is exactly what the Critic brief §5 asks to be promoted.
- Critic C-XC: verdict **Confirmed**, certainty **80%**, severity **Low**.
  Every one of the eleven basis rows is a direct read or a reproduced grep in this checkout, and
  the trigger is not hypothetical — `F-ENG-032` is a checker that is dead in the shipped code and
  `F-XC-005` is a checker disabled by the shipped sample, and neither is visible from the
  endpoint the engine advertises. Held at 80% rather than higher because the *impact* is an
  operator's inability to detect, which is a counterfactual rather than an observed failure, and
  because the 89% ceiling applies (no toolchain, `E1` unreachable). Severity Low, not
  Informational: PROMPT.md §8 puts pure hardening and documentation at Informational, but this is
  the missing detection surface for two Confirmed defects — a "robustness weakness with limited
  impact", which is the Low band. Not Medium: nothing here causes incorrect behaviour on its own.

## QA (QA-XC)

**Not attempted (no toolchain).** Nothing was executed (A9 FALSE).

**PoC written:** `rust-audit/poc/F-XC-010/` — a test for
`crates/sentinel-engine/src/engine/mod.rs` that installs the same Prometheus recorder the engine
installs at boot, runs two full `security_check` calls through the engine's public entry point,
and scrapes `/metrics` after each.

**Why this finding got a PoC when most of the `F-XC` range did not.** Most cross-cutting findings
are configuration or packaging, where a Rust test would be padding — `F-XC-004`'s "the images run
as root" is checked with `docker inspect`, not with `cargo test`. This one earns a test because it
is not an observability wish: it is the reason two Confirmed defects survived unnoticed. The test
therefore does not assert "a metric is missing", which would be trivial. It asserts the
operationally meaningful thing: **a checker whose lookup failed and a checker that examined the
transaction and had no opinion produce byte-identical scrapes**, which is exactly the distinction
`docs/sentinel-engine.md:25` insists must not be conflated.

**What would be run and what it would show.**
`cargo test -p sentinel-engine qa_xc_010 -- --nocapture --test-threads=1`. Single-threading is
required: `safenet_core::observability::metrics::serve` installs a process-global recorder and
succeeds only once per process (`crates/core/src/observability/metrics.rs:13-15`). Nothing else in
`sentinel-engine` installs one — the five `metrics` hits in the crate are all `config.rs` field
references, none a recording call — so the single call is safe today. A passing run converts this
finding to `E1` and prints the scrape body, which is short enough to save verbatim as the
artefact.

**Remediation check — option 1 is sound and is the one to take.** `Checker::name(&self) ->
&'static str` (`crates/sentinel-engine/src/checkers/mod.rs:26-27`) is a closed set of `&'static
str`, matching the label convention every metric in the three existing metrics modules already
follows, so a `checker_outcomes_total{checker, outcome}` counter introduces no cardinality risk.
The finding states its own tradeoff correctly and I agree with its resolution: since `Verdict` has
no error variant (`engine/mod.rs:37-48`), distinguishing `error` from `abstain` needs either a
richer return type or per-checker recording where the error is swallowed, and **the second is
right for now** — it is strictly local, touches only `Err` arms that already `warn!`, and does not
change a public trait four checkers implement. Option 2 is sound but secondary (core already
counts RPC requests globally at `crates/core/src/metrics.rs:26-35`; the value added is
attribution). Option 3 (raise the two verdict lines from `trace!` to `debug!`) is sound as a
stopgap and must not be mistaken for the fix — a per-request log line is not an alertable series,
which is the whole complaint. Option 4 (document it in the configuration table) is sound and free.

I disagree with one line of the finding: "Tests to add: none meaningful". The *absence* is
testable even where the presence would not be worth a unit test, and the PoC above is the
counter-example. It is also the regression guard that tells you the fix landed.

**Certainty: unchanged at 80%.** No new evidence of my own; the PoC is the route to more, and the
89% run ceiling applies regardless.

## Verification (V-XC, Phase 5)

**Outcome: Confirmed by execution, and the observed result is stronger than the finding claims.**

### What I ran

QA-XC's PoC from `rust-audit/poc/F-XC-010/`, appended inside the existing `#[cfg(test)] mod tests`
block at the end of `crates/sentinel-engine/src/engine/mod.rs` (reusing that module's own
`StubChecker`), run, then reverted with `git checkout --`. It compiled as written; no repair was
needed.

```
$ cargo test -p sentinel-engine qa_xc_010 --locked -- --nocapture --test-threads=1
running 1 test
test engine::tests::qa_xc_010_a_failing_checker_and_a_quiet_one_scrape_identically ... --- scrape after a FAILED check ---

--- end ---
ok

test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 106 filtered out; finished in 0.05s
```

The three lines between the two markers are the artefact, and they are the point: **the scrape body
is empty.** Not "contains no checker series" — empty. `safenet_core::observability::metrics::serve`
bound its listener, answered the HTTP request, and returned a zero-byte Prometheus document after a
checker had failed and after a checker had abstained.

Every assertion held:

- `broken_verdict == Verdict::Abstain` and `quiet_verdict == Verdict::Abstain` — a checker whose
  lookup failed and a checker that examined the transaction and had no opinion are the same value
  to the caller, because `Verdict` has no error variant (`engine/mod.rs:37-48`).
- `after_failure == after_abstention` — and they are the same because both are empty. **A checker
  that failed and a checker that had no opinion produce byte-identical scrapes.**
- None of `checker`, `verdict`, `abstain`, `insecure`, `security_check`, `sentinel_engine` appears
  in the body.

### Where the result exceeds the finding

The finding's claim is that the endpoint serves `safenet-core`'s generic JSON-RPC counters plus
tokio runtime gauges, and merely says nothing about checkers. In a process that has performed two
full `security_check` calls, the endpoint served **nothing at all**. The generic counters are
recorded lazily through the `metrics` facade and only materialise once something records them, so
until the engine makes an outbound RPC there is not one series to scrape. An operator pointing
Prometheus at a freshly started engine that is answering checks gets an empty document and no
indication whether the process is healthy, wedged, or has every checker failing.

This tightens the link to the two findings that ride on it. `F-ENG-032` (`RefundChecker` has
abstained on every transaction since it was written, because its synthetic sub-transaction carries
`chain_id = 0`) and `F-XC-005` (the shipped sample's 50,000-block single-call lookback turns the
address-poisoning check into an `Abstain` on any provider error) are both invisible not because the
right series is missing from a populated endpoint, but because there is no series.

### Verdict

**Basis class: `E2` → `E1`.** The finding's claims were established by manifest and grep evidence;
the operational consequence is now executed and its output recorded verbatim above.

**Severity: — / Low — unchanged.** This is an observability gap, not a defect in what the engine
decides. It is the finding that makes several *other* defects undetectable rather than one that
causes harm itself, and the severity should stay where it is for that reason. Its priority,
however, is higher than its severity: it is the cheapest change that would have caught
`F-ENG-032` on day one.

**Certainty: 80% → 97%.** Executed and deterministic. The residual 3% is that the test runs the
engine in-process rather than the shipped binary, so it verifies what `SentinelEngine` and
`observability::metrics::serve` do, not what a deployed `sentinel-engine` does after hours of
traffic (by which time the core RPC counters would have appeared — though still nothing about
checkers).

**Remediation: option 1, as QA-XC assessed it, with per-checker recording at the point the error is
swallowed.** `Checker::name(&self) -> &'static str` (`checkers/mod.rs:26-27`) is a closed set of
`&'static str`, so a `checker_outcomes_total` counter labelled by name and outcome carries no
cardinality risk. Recording locally in the `Err` arms that already `warn!` avoids changing a public
trait that four checkers implement. Option 3 (raising the two verdict lines from `trace!` to
`debug!`) is a stopgap and should not be presented as the fix — the empty scrape above is the
complaint, and a per-request log line is not an alertable series.
