## Claim

The shipped sample sets `address_poisoning_lookback_blocks = 50000`, leaves
`address_poisoning_max_block_range` commented out, and points `rpc` at a public endpoint
(`https://rpc.gnosischain.com`). With `max_block_range` unset, `block_chunks` emits the whole
50,000-block window as a *single* `eth_getLogs` call. If the provider rejects that call for
exceeding its range limit — the case the checker's own doc comment names, quoting an Infura error
verbatim as "range 50000 exceeds limit of 10000" — the failure happens on the *first* chunk, so
`recipients` is still empty, the partial-scan branch is not taken, the error propagates out of
`established_recipients`, and `check` returns `Verdict::Abstain`.

That failure is per-request and permanent: every security check that reaches the
address-poisoning checker abstains, forever, on every transaction. The engine keeps answering
200s, the sentinel keeps voting, and the only signal is one `warn!` line per request. An
operator following the sample gets a deployment in which one of the ten checkers — the only one
that can detect a lookalike-address substitution, the attack class the checker exists for — is
off, and nothing says so.

The sample is self-contradictory on this point: the config comment tells the operator to "set
this to a provider's own documented cap", and the checker's Rust doc explains the arithmetic in
detail, but the sample then demonstrates the combination that only works against a provider with
no cap.

## Trigger

Deploy the engine with the sample config unchanged against any RPC provider whose `eth_getLogs`
range limit is below 50,000. Then send any Safe transaction that reaches the address-poisoning
checker — an ERC-20 `transfer` or `approve` to a fresh address, which is the checker's whole
target shape (`decode_target`). Every such request produces `Verdict::Abstain` from this checker.
Because abstain is indistinguishable on the wire from a deliberate "no opinion" (ENG-H13), the
sentinel cannot tell a disabled check from a check that ran and found nothing, and votes
accordingly.

Second-order, when the provider *does* accept the call: a 50,000-block `eth_getLogs` filtered on
one token address runs on every security-check request, with no cache, no concurrency bound and
no timeout on the provider (ENG-H10). That is a large per-request RPC cost driven by
attacker-chosen transaction contents (A2) against a shared public endpoint, and it is the second
reason the sample's value is a poor default.

## Considered and rejected

- **"The engine would fail loudly at startup."** It does not: `AddressPoisoningChecker::new`
  (`address_poisoning.rs:156-166`) stores the two numbers and performs no probe, and
  `EngineConfig` validates neither (`crates/sentinel-engine/src/config.rs:37-55` — `blocklist`,
  `address_poisoning_lookback_blocks` and the optional `NonZeroU64` are taken as given). The
  first `eth_getLogs` happens on the first request, inside the checker, where the only
  consequence is an abstain.
- **"A partial scan would still work."** Only after at least one chunk has succeeded — the guard
  is literally `Err(err) if !recipients.is_empty` (basis row 4). With a single chunk there is no
  "so far", so the graceful path is unreachable by construction in exactly this configuration.
- **"Abstain is safe, so this is not a security issue."** Abstain is safe in the sense that the
  engine never wrongly affirms; the harm is the silent loss of a detection capability that the
  operator believes is running. The Charter rule the checker enforces produces no verdict at all,
  and `codebase-map.md:203-214` item 8 asks exactly this question of sample configs.
- **"`block_chunks` might loop forever or overflow with `NonZeroU64::MAX`."** It does not:
  `end = start.saturating_add(max_range).min(to)` and `done = end >= to`, with `from <= to`
  guaranteed by `from = current_block.saturating_sub(lookback)`
  (`address_poisoning.rs:189`, `:250-267`). The engine analysis reaches the same conclusion
  (`analysis-sentinel-engine.md:225`) and I re-derived it. Not a finding.
- **Ownership note.** The checker's internals (`address_poisoning.rs`) belong to R9 and the
  engine's `config.rs` to R8; this finding is filed on the sample TOML, which is R10's, and cites
  the Rust only to establish what the sample's values cause.

## Remediation options

1. Change the sample to ship a conservative pair that works against a capped provider — e.g. keep
   `address_poisoning_lookback_blocks = 50000` but *uncomment*
   `address_poisoning_max_block_range = 9999`, so the default configuration is the one that
   survives a 10,000-block cap. Tradeoff: five sequential `eth_getLogs` calls per check instead of
   one, which is slower but is what the chunking exists for.
2. Validate at startup: reject a configuration where `lookback_blocks` exceeds
   `max_block_range` when the latter is set, and warn loudly at `error!` (once, at boot) when
   `max_block_range` is unset and `lookback_blocks` is above some threshold.
3. Make the failure visible rather than silent: emit a metric for checker outcomes
   (`abstain_due_to_error` distinct from `abstain`) — the engine currently exports no metrics of
   its own at all, so an operator has no counter that would move here.
4. Optionally probe once at startup with a single `eth_getLogs` over the configured span and fail
   fast if the provider rejects it, converting a permanent silent degradation into a boot error.

Tests to add: a mocked-provider test asserting that a first-chunk `TransportError` yields
`Verdict::Abstain` and that the same error on a later chunk yields the partial-scan path — the
two branches of basis row 4, neither of which has a unit test today (`address_poisoning.rs` tests
cover only the pure helpers, by the `AGENTS.md` convention).

### The trigger is stronger than the finding claims, and does not need the provider-cap conjecture

I worked the code before reading the argument and reached the same mechanism, but the finding
anchors its trigger on basis row 8 — the unverifiable claim that this specific public endpoint has
a range cap — and therefore reads as weaker than it is. The provider-independent form:

With `max_block_range` unset, `block_chunks` yields **exactly one** chunk. The graceful-degradation
branch at `address_poisoning.rs:202` is gated on `!recipients.is_empty`, and `recipients` cannot
be non-empty before the first (only) call returns. So in the shipped default configuration **the
partial-scan path is unreachable by construction**, and *any* error from that single `eth_getLogs`
— a range-limit rejection, a **rate-limit response**, a timeout, a transient 5xx — is a hard
`Verdict::Abstain` for that request, with no fallback.

A4 puts "stale, rate limited, or incomplete `eth_getLogs` results" explicitly **in** scope, and
both handbooks name rate limiting as an expected operational condition
(`docs/validator-handbook.md:111`, `docs/sentinel-handbook.md:93`: "Rate limits ... can still
prevent full participation"). So the trigger is inside the confirmed assumptions without any
conjecture about a particular vendor. R10 states this fact in the Considered-and-rejected section
("the graceful path is unreachable by construction in exactly this configuration") but does not
promote it into the Trigger, where it belongs. With it, the finding is Confirmed rather than
conditional.

The permanence claim splits accordingly: under a range-limit cap the abstain is permanent; under
rate limiting it is intermittent but correlated with load, i.e. worst exactly when checks matter.

### Two corrections

- **"Silently disables" (title) overstates it.** The failure is logged: `address_poisoning.rs:369-376`
  emits `tracing::warn!(%err, token, candidate, rule, "address-poisoning history lookup failed")`
  once per affected request, and `warn` is emitted at the shipped `log_filter = "info"`. The body
  is accurate ("the only signal is one `warn!` line per request"); only the title is not. What is
  genuinely invisible is the aggregate: the engine crate has **no metrics module and no `metrics`
  dependency** (`ls crates/sentinel-engine/src/` shows no `metrics.rs`; `grep -n metrics
  crates/sentinel-engine/Cargo.toml` is empty), so nothing counts abstentions or checker failures.
  I have promoted that to **`F-XC-010`**, which is the finding that makes this one's degradation
  undetectable in practice.
- **The blast radius is one checker, not two.** `main.rs:70-72` passes the same
  `Arc<AddressPoisoningChecker>` into `RefundChecker::new`, so I expected the refund leg to degrade
  with it. It does not, for an unrelated reason: `refund_transfer` builds its synthetic transaction
  with `..Default::default` (`checkers/refund.rs:104-117`), leaving `chain_id = 0`, so
  `AddressPoisoningChecker::check` abstains at the chain-id guard (`address_poisoning.rs:312-320`)
  before any `eth_getLogs` is issued. That is R9's `F-ENG-032` ("`RefundChecker` is dead"), which I
  verified independently while checking this. Net: the refund leg is already dead, so this finding
  costs the deployment the **primary-transfer** poisoning check only.

### Severity, set on impact rather than on "it is just a sample"

The impact is the loss of the last checker in the chain (`main.rs:56-72`), and the chain
short-circuits at the first non-`Abstain` verdict (`engine/mod.rs:59-70`), so an
address-poisoning abstain is usually the *whole engine's* verdict. Consequences, precisely:

- `Verdict::Insecure` for a genuine lookalike substitution is never produced → the sentinel does
  not deny a poisoning attempt it would otherwise have caught. This is the checker's entire reason
  for existing.
- `Verdict::Secure` from `ExactMatch` is never produced → the sentinel abstains and casts no vote
  (`docs/sentinel-engine.md:19-25`), losing participation and fee income on transactions it could
  have judged.
- It never causes a *wrong affirmation*: abstain is fail-safe, and the engine cannot be pushed
  from `Insecure` to `Secure` by this path.

That last point is what keeps it out of the High/Critical bands — there is no invalid attestation
and no malicious transaction rated `secure`. It is squarely PROMPT.md §8's Medium: "incorrect
behaviour under unusual but reachable conditions ... missing validation with contained impact."

Two interactions the report should carry together. First, `F-ENG-033` (Confirmed by C-ENG-B) shows
this same checker *affirms* `secure` from an attacker-chosen `to`; the two findings point opposite
ways — one makes the checker say nothing, the other makes it say the wrong thing — and both argue
for treating its output as unreliable until the affirmation side is fixed. Second, `F-ENG-009`
(R8) is the same configuration pair read from the other end: too-small a `max_block_range` gives
thousands of sequential calls, too-large (unset) gives one that any capped or rate-limited provider
rejects. Neither value is validated. They should be remediated together — a single
`EngineConfig::validate` covers both — and the report should cite them as a pair.

### Finding verdict

**Confirmed.** Mechanism verified line by line and re-derived independently; trigger verified
inside A4 once the provider-cap conjecture is replaced by "any first-chunk error" (above).

**Certainty: 76%.** Solidly in the `E2` band. Held below the top of it because the *permanence*
of the degradation — as opposed to its occurrence — still rests on basis row 8, and because no
integration test exercises either branch of `established_recipients`' error handling.

**Severity: Medium (unchanged), for the reasons above rather than the ones filed.** I considered
Low on the grounds that a sample is not a deployment and rejected it: the sample is what both the
operator guide (`docs/sentinel-engine.md:39-43`) and the crate's own
`parses_sample_config` test present as the worked example, the identical pair appears in the
engine's own test fixture (`config.rs:75-81`) and in the documentation's inline config
(`docs/sentinel-engine.md:45-76`), and the code ships no validation that would question it. A
default that disables a security control on a capped or rate-limited provider is a defect in the
default, not in the operator.

### Note for QA

Remediation 1 (ship `address_poisoning_max_block_range = 9999` uncommented) is the correct
one-line fix and is strictly safer than the current default on every provider, capped or not.
Remediation 3 depends on `F-XC-010`. The suggested tests — a mocked-provider first-chunk error
asserting `Abstain`, and a later-chunk error asserting the partial-scan path — are the two
branches of basis row 4 and neither exists today; QA should author both even unrun, since
`Provider::mocked` already exists (`core/src/provider/mod.rs:138-140`) and makes them cheap.

## Real-world validation (Phase 8, RW-ENG)

Recorded here because this agent's F-ENG-033 scenario required resolving the tension between the two
findings, and the mechanism was tested directly. The full write-up, including both configurations
back to back, is in `F-ENG-033.md` under the same heading.

### Scenario

Anvil 1.8.1 on `127.0.0.1:8545` (chain 31337), mined to block 15,014 so a 50,000-block lookback
saturates to `fromBlock = 0x0` and still spans the whole chain. A local proxy on `127.0.0.1:8546`
stands in for a capped provider: it rejects any `eth_getLogs` whose `toBlock - fromBlock` span
exceeds 10,000 with the same error text a capped provider returns, and forwards everything else to
Anvil unchanged. The real `sentinel-engine` binary was pointed at the proxy, configured from a copy of
the shipped sample with only `rpc` and `bind_address` rewritten — `address_poisoning_lookback_blocks =
50000` and the commented-out `address_poisoning_max_block_range` left exactly as shipped.

### Verbatim outcome

Shipped sample values, capped provider, an ordinary ERC-20 `transfer` payload:

```
VERDICT: {"verdict":"abstain"}
proxy:   CAPPED eth_getLogs span=15014 > 10000
engine:  {"message": "address-poisoning history lookup failed",
          "err": "server returned an error response: error code -32005: … range 15014 exceeds limit of 10000",
          "token": "0x5FC8…5707", "candidate": "0x90F7…b906", "rule": "R-4.3"}
```

One `warn!` line per request, an HTTP 200, and a verdict indistinguishable on the wire from a
deliberate "no opinion" — exactly as claimed. Setting `address_poisoning_max_block_range = 10000` and
changing nothing else restored the check on the same provider (`proxy: ALLOWED eth_getLogs
0x0..0x2710`), confirming the chunking remedy the sample documents but does not apply.

The "Considered and rejected" entry is confirmed with a nuance worth recording. The engine **does**
fail loudly at startup when the RPC is *unreachable* — `Provider::connect` runs before
`TcpListener::bind`, so with a dead endpoint the process exits 1 with
`Error: Transport(Custom(reqwest::Error { … ConnectionRefused … }))` and nothing ever listens on the
API port (verified: `nothing listening on 5473`). But that is the only startup probe. A provider that
is reachable and merely *caps* `eth_getLogs` passes startup cleanly and fails per-request forever
after, which is precisely the silent case this finding describes. (Note also that the Prometheus
health listener binds *before* the connect attempt, so a health check on that port can observe a
process that will never serve the API.)

### Verdict

**Reproduced end-to-end**, with the caveat that a stand-in capped provider was used: under the Phase 8
safety boundary no live endpoint may be contacted, so row 8 of the Basis table — whether
`rpc.gnosischain.com` *in particular* caps below 50,000 — remains unverified and unverifiable here.
What is now proven is everything the finding depends on besides that: the single 50,000-span call is
issued, a cap rejects it on the first chunk, `recipients` is empty so the error propagates, the verdict
is `Abstain`, the only signal is one warn line, and the documented remedy fixes it.

Certainty **76% → 92%**. The residual uncertainty is entirely the one provider-specific question
(A4). Severity **Medium / Medium**, unchanged.
