## 6. Hypotheses considered and rejected (with the citation that refuted each)

1. **`Watcher::next` can lose a block update when `on_block_update` errors with
   `UnexpectedBlockUpdate`.** Rejected: `index/mod.rs:86-95` calls `on_block_update` only on the
   branch where `next_logs` returned `Ok(None)`, and `EventWatcher::next` returns `Ok(None)` only
   from `Step::Idle` (`events.rs:282-283`). Nothing mutates `step` between those two points, and
   `on_block_update` errors only when `!matches!(self.step, Step::Idle)` (`events.rs:230-232`).
   *Flagged to the Critic:* if this ever became reachable it would be a lost block, because
   `blocks.next` has already popped the queue entry (`blocks.rs:387-389`) by then.
2. **`on_block_invalidated` can mismatch and deadlock the recovery path.** Attempted hard;
   rejected but with residual doubt (recorded as observation O-1). If `revalidate_last_block`
   returned an `InvalidatedBlock` whose hash differed from `Step::Block.block_hash`, the `?` at
   `index/mod.rs:121` would propagate `UnexpectedBlockInvalidation` *after*
   `revalidate_last_block` had already truncated `recent`, rewound `pending`, cleared the queue and
   pushed `Uncle` (`blocks.rs:522-532`) — and every subsequent retry would hit the
   `Some(_) => return Ok(None)` guard at `blocks.rs:488` because the queue front is now an `Uncle`,
   producing a permanent loop. I could not construct a reachable mismatch: the driver alternates
   strictly (`index/mod.rs:85-97`), so `Step::Block`'s hash is always the last emitted `New`, and
   `rposition(|block| next_number.is_none_or(|number| block.number < number))`
   (`blocks.rs:494-497`) selects exactly that block in each queue shape I traced (empty queue;
   `queue.front == New{n+1}` after init with and without `start_block`; after a resume-uncle;
   after a previous revalidation). Left as an observation because the consequence is severe and the
   argument is a case analysis, not an invariant enforced in code.
3. **Duplicate `topic0` values in `Events::topics` cause duplicated logs in `MultipleQueries`.**
   Mechanism confirmed — `events.rs:569-575` concatenates each ABI's `SELECTORS` with no
   de-duplication, and `events.rs:413-439` maps over `self.topics` and `.concat`s, so a repeated
   topic yields the same log twice; `state/mod.rs:207-211` uses a *strict* comparison
   (`(a.block, a.index) < (b.block, b.index)`), so duplicates would be `BadUpdate` and a fail-stop.
   Rejected as a finding because it is not reachable today: `grep -n "event " crates/validator/src/bindings.rs crates/sentinel/src/bindings.rs`
   shows the validator's three ABIs (`Consensus`, `FROSTCoordinator`, `Oracle`) and the sentinel's
   two (`SentinelOracle`, `Consensus`) declare no two events with the same signature. Kept as
   observation O-2 and mentioned in F-CORE-006's "Considered and rejected".
4. **`decode_and_sort`'s `sort_unstable_by_key` gives a non-deterministic order.** Rejected as
   harmful: on a real chain `(block_number, log_index)` is unique, so instability is unobservable;
   and where it would not be unique (the duplicate-topic case above) the state machine rejects the
   batch outright (`state/mod.rs:207-211`) rather than applying either order.
5. **An uncle/warp sequence can skip or duplicate a block.** Rejected. The uncle path rewinds
   `pending` to exactly the uncled block (`blocks.rs:425-428`), so the replacement for that same
   height is fetched next; the block that triggered detection is discarded and re-fetched. `pending`
   advances by exactly one per accepted block (`blocks.rs:538-543`). `Warp` is queued only for
   `from <= safe` (`blocks.rs:271-278`, `279-289`), and the state machine's `is_next_in_range`
   guards (`state/mod.rs:200-234`) reject any gap. The deep-reorg test `blocks.rs:975-1031` asserts
   N uncles followed by N news for an N-deep reorg.
6. **`revalidate_last_block` can invalidate the `safe` anchor and corrupt the window.** Rejected:
   it only ever indexes into `recent` (`blocks.rs:494-502`) and never writes `self.safe`; the
   invariant is documented at `blocks.rs:479-482` and asserted by
   `revalidate_can_invalidate_the_oldest_tracked_block` (`blocks.rs:1168-1204`).
7. **Eviction into `safe` can leave a stale anchor that wrongly accepts a reorged block.** Rejected:
   `blocks.rs:453-462` writes `self.safe` from the evicted header in the same statement that pops
   it, and `evicting_from_recent_promotes_the_block_to_safe` (`blocks.rs:1206-1249`) is a
   regression test written specifically for this.
8. **The `expect`s in my files are reachable panics.** Rejected, all four re-derived:
   `blocks.rs:336` (`recent.pop_front`) — the scan runs at least once because
   `safe = latest.saturating_sub(depth) <= latest_number` (`blocks.rs:246`) and every restart resets
   `number = safe` (`blocks.rs:325`); `blocks.rs:457` — guarded by `len > max_reorg_depth` on the
   line above; `events.rs:97-98` — `NonZeroU64::new` on the literals 100 and 3; `events.rs:342` —
   `div_ceil(2)` of a value ≥ 1 is ≥ 1.
9. **Indexing/slicing on RPC-supplied values can panic.** Rejected: the only index expression in my
   files is `&self.recent[last_index]` (`blocks.rs:502`) whose index comes from `rposition` over the
   same deque; `block_retry_delays.get(index).copied` (`blocks.rs:406`) is bounds-checked;
   `page_size.get - 1` (`events.rs:310`) is on a `NonZeroU64`. No slicing of RPC byte payloads
   happens in `index/`; ABI decoding is delegated to alloy (assumption A6, class `I` territory).
10. **Integer casts on RPC-supplied values truncate.** Rejected for the casts:
    `self.recent.len as u64` (`blocks.rs:453`) widens; `.as_millis as u64`
    (`clock.rs:37`) truncates only past ~584 million years; `EthRpcErrorCode::ResourceNotFound.code as i64`
    (`index/mod.rs:140`) widens a small constant. **Not** rejected for the unchecked *arithmetic* on
    RPC timestamps (`blocks.rs:414`, `427`, `525`, `541`, `549`) — written up in F-CORE-008, together
    with the fact that `Cargo.toml` defines no `[profile]`, so debug panics and release wraps.
11. **Unbounded memory in the retained-header window or the log buffers.** Rejected for the log
    buffers: every fetch is per-block or per-page and the result is consumed immediately
    (`events.rs:402-469`); `queue` is bounded by `max_reorg_depth + 2` by construction. **Not**
    rejected for `recent`: it is bounded by `max_reorg_depth`, which is an unvalidated `u64` —
    F-CORE-009, case 2. Also note `BlockUpdate::New` and `Step::Block` each carry a 256-byte `Bloom`
    (`blocks.rs:102-106`, `events.rs:190-195`), which the `#[allow(clippy::large_enum_variant)]`
    comments acknowledge; that is a constant factor, not growth.
12. **The bloom integrity check could be wrong (parity with the header bloom).** Rejected as a
    correctness claim: `compute_logs_bloom` is `alloy::primitives::logs_bloom`
    (`bloom.rs:38-40`), a dependency whose internals are not on disk (A6 ⇒ class `I`). The
    dual-`sha2` note in `state/baseline.md` §6 is irrelevant here — the bloom is keccak-based and no
    SHA-256 is involved anywhere in `index/`; `grep -rn "sha2\|Sha256" crates/core/src/index/`
    returns nothing. Recorded as observation O-3 that the *production* function is never anchored
    against a real header bloom by any test (the Gnosis vector at `bloom.rs:72-522` exercises
    `Bloom::accrue_raw_log` directly, and the two `use_client_filtering` tests compute both sides of
    the equality with `compute_logs_bloom` itself, so they cannot detect a divergence).
13. **`ObservabilityTransport` leaks secrets into logs.** Rejected: `provider/mod.rs:86-94` traces
    the JSON-RPC request and response at `trace` level. The payloads are chain data and signed,
    already-public transactions; the signer key never crosses the transport. Recorded as observation
    O-4 (volume, not confidentiality).
14. **The cached `chain_id` can go stale and mis-sign transactions.** Rejected as a *core-index*
    finding: `provider/mod.rs:135` reads it once and `get_chain_id` returns the cache
    (`163-165`), which is the point — it prevents per-transaction RPC calls. An endpoint silently
    switching chains is undetected, but nothing in `index/` consumes `chain_id` except
    `BlockTime::resolve` at startup (`blocks.rs:205`). This is analysis H17 (no chain-id binding of
    the database) and belongs with R2/R10; recorded as observation O-5.
15. **Cancel-safety of `Watcher::next` under the driver's `select!`.** Rejected. `blocks.rs:387-389`
    returns queued updates before any await; `index/mod.rs:93-95` has no await between
    `blocks.next` resolving and `on_block_update`; `events.rs:324-325` and `382-383` assign
    `self.step` only after `fetch_logs` completes; `blocks.rs:504-533` mutates only after its await.
    The only state a dropped future can leave behind is `pending.timestamp_ms += block_time`
    (`blocks.rs:414`), which delays the next poll by one block time — cosmetic.
16. **`start_block` inside the reorg window double-emits or skips.** Rejected: the filter at
    `blocks.rs:345-358` emits exactly the recent blocks `>= start_block`, and
    `only_emits_blocks_at_or_after_start_block_inside_reorg_window` (`blocks.rs:787-809`) and
    `does_not_warp_when_start_block_is_within_reorg_window` (`blocks.rs:760-785`) assert both edges.
    **Not** rejected for `start_block > latest`, which is silently ignored — F-CORE-009, case 3.
17. **`max_reorg_depth = 0` lets a warp cover an uncleable block.** Confirmed as behaviour
    (`supports_no_reorg_protection`, `blocks.rs:811-837`, warps to `safe == latest`, contradicting
    the comment at `blocks.rs:268-270`) but rejected as a defect: at depth 0 the operator has
    declared no block mutable, and any later reorg is caught by `blocks.rs:435-439`. Noted inside
    F-CORE-005's "Considered and rejected".
18. **`check_logs_limit` is missing on the `ClientFiltered` path.** Confirmed
    (`events.rs:441-466` never calls it) but rejected as a separate finding: a truncated response
    removes bloom bits, so the equality check at `events.rs:450` catches it more strongly than a
    count threshold would. Mentioned inside F-CORE-002.
19. **`Filter::at_block_hash` vs `from_block`/`to_block` encoding could be wrong.**
    Not assessable offline: `alloy` 2.0.5 sources are not on disk (A6). Class `I`, no finding.
    Listed here so the Coverage Critic knows it was considered and why it was dropped.

## 7. Observations (plausible, below the finding bar)

- **O-1 — `UnexpectedBlockInvalidation` would deadlock the `-32001` recovery if it were ever
  reachable.** See rejected hypothesis 2. The failure mode is a permanent loop, not a crash, and the
  argument that it cannot happen is a case analysis over queue shapes rather than an assertion in
  code. A cheap hardening would be to make `Watcher::next_logs` tolerate
  `UnexpectedBlockInvalidation` (the block watcher has already been rewound at that point, so the
  correct action is to return `Ok(None)` and let `blocks.next` deliver the queued `Uncle`), or to
  `debug_assert!` the hash equality inside `revalidate_last_block`. Recommended for the Critic to
  re-derive independently.
- **O-2 — `Events::topics` does not de-duplicate.** `events.rs:569-575`. Latent: two watched ABIs
  sharing an event signature would make `MultipleQueries` return every matching log twice and turn a
  transient RPC failure into a `BadUpdate` fail-stop. The crate's own test fixture `TokenEvents`
  (`events.rs:632-638`) has exactly this shape (`Erc20::Transfer` and `Erc721::Transfer` share
  `Transfer(address,address,uint256)`), so the hazard is one `watcher_events!` edit away. No service
  is affected today.
- **O-3 — the production bloom function is never anchored against a real header bloom.**
  `bloom.rs:72-522` validates `Bloom::accrue_raw_log` against Gnosis block 45195961, not
  `compute_logs_bloom`; `events.rs:932` and `1361` compute the expected value with
  `compute_logs_bloom` itself, so a divergence between `alloy::primitives::logs_bloom` and the
  header's accumulation rule would pass every test and reject every block in production. A one-line
  test asserting `compute_logs_bloom(<the 45195961 logs>) == <that block's header bloom>` would close
  it.
- **O-4 — `trace`-level RPC logging is unbounded in volume.** `provider/mod.rs:86-94` formats the
  full request and response JSON of every call. The integration scripts enable `safenet_core=trace`
  (`scripts/lib/shared_test_scripts.sh:156`), so an operator copying that setting would log every block
  and log batch in full. No secret exposure (the payloads are public chain data and signed
  transactions), so this is disk/throughput, not confidentiality.
- **O-5 — no chain-id or deployment binding anywhere on the index path.** `provider/mod.rs:135`
  caches the chain id and nothing persists it; `BlockTime::resolve` (`blocks.rs:34-43`) is the only
  consumer inside `index/`. Analysis H17; belongs with the persistence reviewers. Folded into
  F-CORE-001's remediation option 4 as a secondary suggestion rather than claimed separately.
- **O-6 — `fallible_events` is permanent, unmarked event loss.** `events.rs:426-436` drops a failed
  per-topic query's logs and the surrounding update is still committed as complete for the range.
  Unused by any service today (section 5), so this is a documentation issue: the `Config` doc
  comment (`events.rs:89-91`, "Use this to mark events as noncritical") understates it — enabling
  the option accepts permanent, silent loss of those events, not merely a downgrade in priority.
- **O-7 — `BlockWatcher` never checks that a returned header's `number` matches the number
  requested.** `blocks.rs:227-236` copies whatever the node returns and `blocks.rs:441-447` records
  it. A node answering `eth_getBlockByNumber(n)` with a header for a different height would corrupt
  `recent` and `pending`, and the state machine would then fail-stop with `BadUpdate`
  (`state/mod.rs:190-199`). Not filed: under A4 the RPC is not malicious, and the outcome is a
  fail-stop rather than silent divergence. A one-line `if block.number != number` check in
  `require_block` would remove the class entirely.
- **O-8 — `status.latest` reports the node's head before any of it has been processed.**
  `blocks.rs:376-381` derives `latest` from `pending.number - 1`, and `initialize` sets `pending`
  from the node's head at `blocks.rs:253` *before* the queue of `Uncle`/`Warp`/`New` updates is
  drained. The driver feeds that value to `TransactionQueue::update_block_status` on the very first
  update (`driver.rs:240-247`), so on startup the transaction queue reconciles against a block the
  state machine has not reached. Whether that matters is a transaction-queue question (R3, and
  Manager lead M10), so it is recorded rather than claimed here.

## 8. Coverage gaps and caveats

- **No `E1` evidence anywhere.** Every finding is `E2` (cited code plus a concrete trigger) or, where
  stated, `I`. `cargo test -p safenet-core` was not run; where the Reviewer role calls for running
  targeted tests, the tests were read instead and what they prove (or fail to prove) is stated in the

  `ProviderCall::Ready` short-circuits every internal chain-id fetch — are marked `I` and are not the

  alloy.

  dispatch. I re-read `validator/src/state/mod.rs:400-470` to confirm the mechanism, but the

  file it, the Coverage Critic should promote this line.
