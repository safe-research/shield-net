## Hypotheses considered

### Confirmed (promoted to findings)

- **VAL-H1 / checklist 1 — no PoP on `q`.** Confirmed and strengthened. The analysis's chain
  (`analysis-validator.md:231-247`) assumed the attacker publishes shares it cannot encrypt and
  is therefore excluded; re-reading `state/keygen.rs:660-712` shows complaints are also accepted
  in `RolloverState::CollectingShares` with **no deadline guard at all**, so the attacker can
  harvest every pad *before* publishing its own share and then publish a fully valid one. The
  group finalizes with the attacker inside and undetected. → **F-VAL-001**.
- **VAL-H5 / M2 / M3 — two-time pad, raw x-coordinate, doc drift.** Confirmed by
  `frost/ecdh.rs:110-121` + the crate's own `ecdh_is_commutative` test (`ecdh.rs:154-163`),
  `frost/keygen.rs:196-214` and `353-386`, against `docs/overview.md:48`. → **F-VAL-002**.
- **Checklist 7 — complaint-flow policy.** `state/keygen.rs:734-745` responds unconditionally;
  the `CollectingShares` arm has no deadline; the threshold is counted per accused only
  (`714-731`). → **F-VAL-003** (the parts not already inside F-VAL-001).
- **VAL-H4 / checklist 3 — a lost `KeyGenSetup` resume during genesis stalls the network.**
  Confirmed and strengthened. The analysis's trigger was a restart in a ~1-block window (class `I`,
  55%); re-reading `service/effect.rs:126-143` and `243-255` gives a deterministic `E2` trigger
  that needs no crash at all — `Effect::KeyGenSetup` writes to the shared SQLite pool and **any**
  error is collapsed into `Resume::Noop`, while `crates/core/src/effects.rs:53-62` spawns each
  effect exactly once with no retry. Genesis then has no recovery arm whatsoever: all four branches
  of `handle_key_gen_timeouts` require a deadline (`state/keygen.rs:1003-1010`, `1027-1033`,
  `1047-1053`, `1070-1077`) and `handle_rollover_new_block` returns early because
  `EpochId::Genesis::number` is `None` (`912-921`, `consensus/epoch.rs:39-45`).
  → **F-VAL-004**. Observation O1 is superseded by this finding.

### Rejected, with the citation that refutes each

- **M1 — replayed keygen reuses the same key and produces the same ciphertexts / can two
  different share values ever be padded with the same `(sk_me, q_peer)` pad through replay?**
  **Refuted for the replay path.** `store_keygen_secrets` has exactly one non-test caller,
  `service/effect.rs:135-138`, reached only from `Effect::KeyGenSetup { group_id, .. }`, which is
  emitted at exactly one site, `state/keygen.rs:1149-1153` in `start_key_gen`, with
  `group_id = group.id`. The row is therefore keyed by the ceremony's group id
  (`secrets/store.rs:105-124`, insert-only). Within one group id: `sk_me` and the polynomial are
  fixed by that row; `q_peer` is fixed because `FROSTParticipantMap.register`
  (`contracts/src/libraries/FROSTParticipantMap.sol:146-148`) requires
  `state.status == ParticipantStatus.NONE`, so a peer publishes exactly one commitment (hence one
  `q`) per group id; `id_peer` is fixed by the address (`frost/participants.rs:16-19`). Same pad
  **and** same plaintext ⇒ byte-identical ciphertext, which is a replay, not a two-time pad.
  Across group ids: `restart_key_gen_excluding` (`state/keygen.rs:1188-1225`) always removes at
  least one address from the set, so the participants Merkle root and `count` change
  (`consensus/group.rs:140-160,244-264`) and the group id changes, giving a fresh row and a fresh
  `EncryptionKey::generate` (`frost/keygen.rs:54`). The PR #851 recovery path
  (`state/keygen.rs:997-1024`) explicitly does **not** restart when no participant is missing to
  exclude — it skips the epoch — precisely to avoid recomputing an identical group. So no two
  *different* share values are ever padded with the same `(sk_me, q_peer)` pad via replay or
  restart. *(Store-internal properties of `store_keygen_secrets` — the `ON CONFLICT … DO UPDATE
  SET secrets = keygen_secrets.secrets` idiom, JSON-at-rest, zeroisation of the returned
  `String` — are `secrets/store.rs` and therefore R5's; I read them only for this trace and file
  no finding on them.)*
  **Same-pad-two-plaintexts does exist, but from a different cause:** two peers publishing the
  *same* `q` in one ceremony make `me` encrypt `f_me(P1)` and `f_me(P2)` under the identical pad
  (`frost/keygen.rs:196-214`). That is peer-controlled, not replay-controlled, and is covered by
  F-VAL-001/F-VAL-002.
- **VAL-H7 — `ReconcileGroupSecrets` races the same block's store writes.** `service/effect.rs`
  and `state/mod.rs` command ordering are R6's files; the only part in my scope is that
  `Effect::KeyGenSetup` and `Effect::NonceTree` are emitted from Logs transitions
  (`state/keygen.rs:1149-1153`, `1320`) and `Effect::StartNonceGeneration` from `confirm_key_gen`
  (`1352-1355`). I could not construct a deterministic interleaving from my files alone.
  Recorded as **Observation O2**; left to R6.
- **VAL-H9 — late-complaint asymmetry excludes the honest plaintiff.** Partly refuted as stated.
  The analysis cites `state/keygen.rs:692-695` for "complaints after `deadlines.complain` are
  ignored"; the guard is real (`692-695`: `block <= deadlines.complain`), but the analysis missed
  that the **`CollectingShares` arm (`662-684`) has no deadline guard**, so a complaint filed
  before the share round closes is always processed. The residual case — a complaint filed onchain
  after `deadlines.complain` while the local state is `CollectingConfirmations` — is real: the
  accused never queues a response (`711` returns early), the plaintiff cannot confirm onchain
  (`FROSTParticipantMap.sol:219-222` requires `state.complaints == 0`), and the confirm-deadline
  branch (`1087-1090`) then excludes the plaintiff. Impact is one wasted DKG round plus the
  exclusion of a possibly-honest validator; every honest node computes the same deadlines from
  event block numbers, so there is no consensus divergence. Folded into **F-VAL-003** as the
  deadline-asymmetry half rather than filed separately.
- **Threshold / participant-set arithmetic off-by-one (checklist 8).** Refuted.
  `min_participants` (`consensus/group.rs:227-240`) computes `max(2, 2N/3 + 1)` in `u32` and is
  compared against the **post-exclusion** count while `N` is the **pre-exclusion** epoch set
  (`177-217`, esp. `206-212`), which is exactly "strictly more than two thirds of the epoch's
  default set" as documented at `1-38`. Hand-checked N = 0,1,2,3,4,5,6,7,9: `2N/3+1` is the least
  integer strictly greater than `2N/3` in every case. Empty and singleton sets are rejected
  (`min_participants(0) = min_participants(1) = 2 > count`), so `MerkleTree::build` is never called
  with an empty leaf set from this path. `group_threshold = count/2 + 1` (`220-222`) is a strict
  majority for every `count` (test `330-335`), and the contract independently requires
  `count >= threshold && threshold > 1` (`FROSTCoordinator.sol:347`).
- **Group id / context / participant-leaf encoding vs Solidity (A7).** Refuted.
  `group_id` (`consensus/group.rs:252-264`) is `keccak256` over four 32-byte words with the two
  `uint16`s right-aligned at `[62..64]` and `[94..96]`, then `id.0[24..].fill(0)`; this is
  byte-for-byte `FROSTGroupId.create` + `mask`
  (`contracts/src/libraries/FROSTGroupId.sol:36-60`, mask
  `0xffff…ffff0000000000000000` = clear the low 64 bits). Participant leaves are the left-padded
  address word (`consensus/group.rs:244-247`) matching
  `FROSTParticipantMap.register`'s `bytes32(uint256(uint160(participant)))`
  (`FROSTParticipantMap.sol:149`). `group_context` packs `(uint32 0, address, uint64)` into
  exactly 32 bytes (`268-277`) and has no Solidity counterpart (the contract treats `context` as
  opaque, `FROSTCoordinator.sol:343-354`). The `actual_group` test (`group.rs:376-458`) pins the
  whole derivation against a real mainnet transaction.
- **Marshal round-trip canonicality (checklist 12).** Refuted for the cases I could reach.
  `frost_scalar` rejects `>= n` via `Scalar::from_repr` (`marshal.rs:125-129`); `frost_point`
  maps `(0,0)` to the identity and otherwise builds a 65-byte uncompressed SEC1 that `k256`
  validates against the curve equation (`133-148`); `frost_signing_commitments` rejects identity
  in either commitment (`163-176`); `EncryptionPublicKey::from_point` rejects identity
  (`ecdh.rs:70-75`), so `commitment.q` can never be the identity even though `frost_point` allows
  it. The fixed-size slice writes at `140-143` and the `as_chunks::<32>` at `78-81` are over
  constant-length buffers (65-byte uncompressed encoding), so no panic is reachable.
- **Identity coefficient commitments accepted (`marshal.rs:136-138`).** Considered and rejected as
  a finding. A participant may publish `C[0] = identity` (contributing `a_0 = 0`) and still pass
  `verify_proof_of_knowledge`, because a Schnorr PoK over the identity is satisfiable with
  `mu·G = R`. It does not enable biasing the group key: the PoK forces the attacker to know
  `dlog(C[0])`, so it cannot choose `C[0] = kG - Σ_j C_j[0]` for an unknown `Σ_j`. With at least
  one honest contributor the group key stays uniform. Recorded as **Observation O3**.
- **Address→identifier collision / forgery (checklist 1).** Refuted as a practical concern.
  `Identifier::derive(address.as_slice)` (`frost/participants.rs:16-19`) is the ciphersuite HID
  over the 20-byte address, matching the contract's `FROST.identifier`. A collision would silently
  merge two entries in `peer_packages` (`frost/keygen.rs:499-516`, a `BTreeMap<Address, _>` folded
  into a `BTreeMap<Identifier, _>`) and desynchronise the encrypted-share index between
  `generate_secret_shares` (`196-214`) and `verify_encrypted_secret_share` (`365-374`); finding
  such a collision is a 128-bit birthday problem over an attacker-chosen address, which is not
  reachable. An identifier cannot be *forged*: the contract binds `msg.sender` into every event
  and the Rust derives the identifier from that address, never from attacker-supplied bytes.
- **Encrypted-share index desynchronisation between sender and receiver.** Refuted.
  The sender orders `commitments` (a `BTreeMap<Address, _>`, i.e. ascending address) and drops the
  entry whose identifier equals its own (`frost/keygen.rs:196-204`); the receiver walks the same
  map, drops the *sender's address*, and takes the position of its own identifier
  (`365-374`). These agree because the sender's own address is necessarily a key of the map (it
  published the commitment that put it there) and identifier derivation is injective in practice.
  Both sides use the map that `finalize_key_gen_commitments` built from the full commitment set
  (`state/keygen.rs:1247-1290`), which is only reached when `commitments.len == count`
  (`state/keygen.rs:196-213`), and the contract independently enforces
  `share.f.length == state.count - 1` (`FROSTCoordinator.sol:429-431`). An out-of-range index
  returns `IncorrectNumberOfShares` rather than panicking (`frost/keygen.rs:375-378`).
- **Missing length check on `commitment.c` in `verify_commitment`.** Refuted as reachable harm.
  The Rust deliberately skips it (`frost/keygen.rs:83-85`) and the contract enforces
  `commitment.c.length == state.threshold` (`FROSTCoordinator.sol:378`). A zero-length `c` would
  make `verify_proof_of_knowledge` fail or error inside `frost-core` rather than panic — but that
  is upstream behaviour I cannot read (A6), so the claim is class `I`, not `E2`. Recorded as
  **Observation O4**.
- **Panics / casts / arithmetic in my files.** Swept and refuted:
  `consensus/group.rs:142-146` (`try_into.expect`) is bounded because `participants_set` already
  passed both `u16::try_from` gates at `206` and `211` before a `ParticipantSet` can exist;

- **Genesis restart producing an unauthorised group id.** Refuted — `restart_key_gen_excluding`

  `event.accused` says without checking `group.participants.contains(&event.accused)`. Under the

  `commitments` map for a group the contract will never re-emit `KeyGenCommitted` for — the round
  then stalls to the commitment timeout, `exclude_all_others(∅)` excludes everyone, and the epoch
  is skipped or genesis halts. Conditional on R6's finding; recorded here so it is not lost.
- **O8 — `handle_epoch_staged`'s `WaitingForGenesis` recovery trusts the event's `proposedEpoch`**
  (`state/keygen.rs:613-635`). A staged epoch observed before genesis jumps the validator straight
  to `EpochSkipped { next_epoch }` using an attacker-influenced number if event-address binding is
  missing (VAL-H2). Under the contract the value is authenticated. Conditional on R6's finding.
- **O9 — no membership check on the addresses carried by DKG events.**
  `handle_key_gen_committed` inserts `event.participant` into `commitments` after
  `verify_commitment` alone (`state/keygen.rs:173-175`); `handle_key_gen_confirmed` inserts
  `event.participant` into `confirmations` with no check at all (`448`);
  `handle_key_gen_complained` inserts `event.accused` into `complaints` with no check (`714`).
  None of the three consults `group.participants`. Under A7 this is sound — the contract's
  `register` verifies a Merkle proof against the participant root that the group id itself commits
  to (`FROSTParticipantMap.sol:146-150`, `FROSTGroupId.sol:36-51`), and the validator only
  processes events whose `gid` equals the group it derived from its own config — so contract
  membership and local membership coincide exactly. It becomes reachable under VAL-H2 (R6): an
  injected `KeyGenConfirmed` from a non-member would push `confirmations.len` to `count` early,
  and `handle_key_gen_confirmed` would then call `finalize_key_gen(…, status.key_share)` with a
  `Collecting` status whose `key_share` is `None` (`1414-1423`), silently leaving the validator
  out of the new epoch. Listed as a defence-in-depth remediation in F-VAL-003 option 4.
- **O10 — doc-comment inaccuracy in `handle_key_gen_secret_shared`.** The function doc says share
  collection "still completes once every participant has submitted one (valid or not)"
  (`state/keygen.rs:267-274`), but the round-close gate counts `public_keys`
  (`351`), which is only populated when `verify_secret_share` succeeds (`303-306`). A share with a
  bad `y` therefore does **not** count and the round stalls to the timeout instead — which is what
  the inline comment at `294-297` correctly says. Comment-only; no behavioural defect. Flagged so a
  Critic reading the doc does not mistake it for a missing branch.
