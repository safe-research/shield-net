## Hypotheses considered and REJECTED

Each entry names the citation that refuted it.

### From the map / analysis (my assigned leads)

- **ENG-H10 "no timeouts" — CONFIRMED, filed as F-ENG-005.** Not rejected. The
  analysis's claim is accurate: `api/mod.rs:48-50` discards the parsed budget,
  `api/mod.rs:25-31` adds only `TraceLayer`. Refinement the analysis missed:
  `crates/sentinel-engine/Cargo.toml:7-21` does not take the workspace's `tower` and takes
  `tower-http` with only the workspace `trace` feature (root `Cargo.toml:24`), so
  `TimeoutLayer`, `ConcurrencyLimitLayer`, `RequestBodyLimitLayer` and `CatchPanicLayer`
  are not merely unused — they are not compiled in.
- **ENG-H11 "unbounded recursion in `decode_target_effects`" — CONFIRMED AS LATENT ONLY,
  filed as F-ENG-006 at Low.** The reachability shield is real and I re-derived it rather
  than trusting the analysis: `decode_target_effects` (`target_effects.rs:46-52`) is
  called from exactly one place, `excessive_approval.rs:20` (grep over `crates/`, no other
  caller), which is checker #6 (`main.rs:63`); `decode_multi_send_call`
  (`multi_send.rs:143-151`) recurses only into `Operation::DelegateCall` sub-calls; and
  `check_multi_send` (`base.rs:205-213`, checker #3 at `main.rs:60`) requires every sub-tx
  to satisfy `check_calls(sub_tx) || (allows_delegate_calls && check_delegate_calls(sub_tx))`
  — a nested MultiSend sub-call fails `check_calls` (`base.rs:88-90`, not a `Call`) and
  fails `check_delegate_calls` (`base.rs:151-192`, a MultiSend address is in none of
  `MIGRATION_CONTRACTS`/`SIGN_MESSAGE_LIBS`/`CREATE_CALL_CONTRACTS`), so base returns
  `Insecure R-4.2` and the chain breaks at `engine/mod.rs:66-68`. **Maximum reachable
  recursion depth is therefore 2**, not unbounded.
- **ENG-H12 "shutdown is not graceful" — CONFIRMED, filed as F-ENG-007** (`main.rs:79-84`,
  no `.with_graceful_shutdown`).
- **ENG-H13 "failure-abstain indistinguishable from policy-abstain" — CONFIRMED as a fact
  but NOT filed by me.** `engine/mod.rs:46-47` shows `Verdict::Abstain` is a unit variant
  with no reason field, so the two are the same bytes. The *mechanism* that makes it
  matter, however, lives entirely in `checkers/address_poisoning.rs` and `checkers/cow.rs`
  (R9's scope) and in the sentinel's metric (R7's). I record it here as an observation so
  it is not lost, rather than filing a duplicate against R9's files.
- **ENG-H14 "docs understate external dependencies" — NOT FILED, out of bounds.** The
  brief §4 lists `docs/` as reference-only material with no findings on it. The claim is
  true (`docs/sentinel-engine.md` line ~88: "The address-poisoning check (the only check
  backed by RPC-derived state)" while `checkers/cow.rs` makes outbound HTTPS), but it is a
  `docs/` defect. Recorded as an observation for R10/documentation. The *machine-readable*
  half of the same problem — `openapi.yaml`, which IS in my scope — is filed as F-ENG-008.
- **"Panics/500s from malformed bodies or calldata: none found" (analysis §8) — I
  RE-DERIVED THIS INDEPENDENTLY AND AGREE for my files.** A grep for
  `unwrap|expect(|panic!|unreachable!|todo!|assert|as (u|i|f|usize)|from_slice|<<|>>`
  over all eleven assigned `.rs` files returns, outside `#[cfg(test)]`, only:
  `multi_send.rs:106` `Address::from_slice(cursor.read(20)?)` (exactly 20 bytes or `None`,
  `multi_send.rs:181-185`), `multi_send.rs:107-108` `U256::from_be_slice(cursor.read(32)?)`
  ×2 (exactly 32 bytes; `from_be_slice` panics only above 32), `multi_send.rs:109`
  `Bytes::copy_from_slice(cursor.read(data_len)?)` (bounds-checked before the copy),
  `multi_send.rs:171` `unwrap_or_else` (not a panic), and `transaction.rs:37` `*self as _`
  on a fieldless `#[repr(u8)]` enum. **There is no `unwrap`, `expect`, `panic!`,
  `unreachable!`, `todo!`, index or slice expression in non-test code anywhere in my
  scope.** The decoders are total.
- **"Unbounded allocation from an attacker-supplied length field" (my own lead, and the
  headline risk the launch message flagged) — REFUTED for `decode_multi_send`.**
  `multi_send.rs:108` converts the 32-byte `dataLength` via
  `U256 -> usize try_into.ok?`, and `multi_send.rs:109` then passes it to
  `Cursor::read`, which is `mem::take(&mut self.0).split_at_checked(len)?`
  (`multi_send.rs:181-185`). `split_at_checked` returns `None` **before** any allocation
  when `len` exceeds the remaining bytes, so `Bytes::copy_from_slice` never allocates more
  than the input already contains. A `dataLength` of `2^40` on a 1 KiB body allocates
  nothing and returns `None`. Memory is O(body), not O(declared length).
- **"A MultiSend whose declared length disagrees with its actual bytes" — REFUTED as a
  hazard.** Every read in `decode_multi_send` (`multi_send.rs:99-130`) goes through the
  same checked cursor; truncation mid-entry, a trailing partial entry, or an oversize
  `dataLength` all return `None` from `decode_multi_send`, which `decode_multi_send_call`
  turns into `None` (`multi_send.rs:160-163`) and `base.rs:206-208` turns into
  `Insecure R-4.2`. No panic, no partial state.
- **"Zero-length / truncated / oversize calldata" — REFUTED.** `data.is_empty` is an
  explicit early return (`target_effects.rs:68-70`); a `dataLength` of 0 yields
  `split_at_checked(0) == Some((&[], rest))`; an entirely empty blob yields
  `Some(vec![])` (the `while let Some(operation) = cursor.next` at `multi_send.rs:99`
  never enters); calldata shorter than 4 bytes fails every `abi_decode` in
  `target_effects.rs:71-129` and every `starts_with(SELECTOR)` in `base.rs`.
- **"`operation` byte outside {0,1} in a packed sub-transaction" — REFUTED.**
  `multi_send.rs:100-104` returns `None` for anything but 0/1. At the JSON layer,
  `transaction.rs:41-50` rejects it at deserialisation (pinned by
  `transaction.rs:165-169`), so the handler never runs.
- **"Body-size / JSON-depth bomb" — NOT REFUTABLE OFFLINE, downgraded to an observation.**
  `api/mod.rs:25-31` sets no `DefaultBodyLimit`, so axum 0.8.9's default (documented as
  2 MiB) applies, and `serde_json` 1.0.150 has its own recursion cap. Both are class `I`
  under A6 (no registry on disk). All quantities are hex *strings*
  (`transaction.rs:59-75`), not JSON numbers, so there is no numeric-parse blowup.
- **"Header injection / oversized header values" — REFUTED.** `extractors.rs:52-69` is
  the only header code: absent header -> `Ok(None)`; present -> `HeaderValue::to_str`
  (rejects non-visible-ASCII) then `T::from_str`, both mapped to a fixed
  `(StatusCode::BAD_REQUEST, &'static str)` (`extractors.rs:18,22-25,39,43-46`). No
  attacker string is echoed into the response, into a log field, or into a URL. Both
  extractors run **before** the `Json` body extractor (`api/mod.rs:33-37`), so a bad
  header short-circuits before the body is read. `Duration::from_millis(u64::MAX)`
  (`extractors.rs:48`) cannot panic. A duplicate header takes the first value
  (`HeaderMap::get`) — no smuggling surface here, since the engine is the terminal server.
- **"`x-request-id` reflected into logs unsanitised" — REFUTED.** `api/mod.rs:44-46`
  records it only after it has parsed as a `B256` (`extractors.rs:21`), i.e. 32 bytes
  re-rendered by alloy's `Display`. Arbitrary text cannot reach the span field.
- **"Wire drift between `openapi.yaml` and the handler's *schemas*" — REFUTED for the
  happy path.** Field-by-field: `openapi.yaml:101-128` lists the same twelve `camelCase`
  members as `transaction.rs:56-76`, both `additionalProperties: false` /
  `deny_unknown_fields`; `openapi.yaml:54` `required: [block, transaction]` matches
  `api/mod.rs:16-22`; `openapi.yaml:129-133` `Operation enum [0,1]` matches
  `transaction.rs:20-29`; `openapi.yaml:161-168` `RuleId` pattern `^R-[0-9]+\.[0-9]+$`
  admits all six `rule.rs:105-114` codes; `openapi.yaml:86-95`'s
  `secure`/`insecure`/`abstain` discriminator matches `engine/mod.rs:36-48`'s
  `tag = "verdict"`, `rename_all = "lowercase"`; and `openapi.yaml:4` `version: 0.2.0`
  matches `crates/sentinel-engine/Cargo.toml:3`. The gap is in the **response set** and
  the timeout semantics only — F-ENG-008.
- **"Impl stricter than the spec (would reject honest sentinel traffic)" — REFUTED; the
  drift is the other way.** `openapi.yaml:169-174` `Digest` is lower-case-only and
  `0x`-required while `B256::from_str` accepts either case; `openapi.yaml:181-186`
  `Quantity` demands minimal lower-case hex while ruint accepts more. Being *more*
  permissive than the published contract cannot reject a conforming caller.
- **`safenet_guard::AnnouncedTransaction` selector mirror — REFUTED as a defect.**
  `bindings.rs:42-52` declares `address to; uint256 value; bytes data; uint8 operation;
  uint256 safeTxGas; uint256 baseGas; uint256 gasPrice; address gasToken; address
  refundReceiver`, field-for-field and in order identical to
  `contracts/src/libraries/TransactionAnnouncement.sol:27-37`, whose `Enum.Operation`
  ABI-encodes as `uint8`. The derived selector is therefore right (the `uint8`-for-enum
  step is class `I`: the Solidity ABI rule, not something I executed).
- **"Charter networks vs the engine's supported chain set" — REFUTED.** Article I
  (`safenet-charter@44a1e53:Safenet_Arbitration_Charter.md:36-41`) scopes the rules to
  "Ethereum / Arbitrum / Gnosis Chain", which is exactly the `{1, 100, 42161}` set
  `checkers/cow.rs:88` claims. (`cow.rs` is R9's file; recorded so the claim is not
  re-litigated.)
- **"R-4.6 is cited as Article IV Part B but might be Part A" — REFUTED.** The Charter has
  `### Part A — Deterministic rules` at line 490 covering R-4.1 (500) and R-4.2 (546), and
  `### Part B — Target manipulation` at line 577 covering R-4.3 (588), R-4.4 (611),
  R-4.5 (635) and R-4.6 (659) with no third Part heading. Every Part attribution in
  `rule.rs:16,20,24,28,58,69` is correct.
- **"`RuleId` round-trip / serialisation defect" — REFUTED.** `rule.rs:83-101` serialises
  via `code` and deserialises via `from_code`, rejecting unknown codes with a
  `de::Error::custom`; `rule.rs:137-163` pins both directions for all six variants and the
  rejection message. The `Verdict::Insecure { rule: RuleId }` type (`engine/mod.rs:42-45`)
  makes "insecure without a rule code" unrepresentable.
- **"`block` can widen the address-poisoning scan window" — REFUTED (and it is R9's file
  anyway).** `CheckContext` carries only `block: u64` (`engine/mod.rs:23-33`) and
  `api/mod.rs:52-54` copies it straight from the request; the window arithmetic
  (`address_poisoning.rs:189,192`) is `to.saturating_sub(lookback) ..= to`, whose span is
  `<= lookback` for every `u64`.
- **"`CheckRequest` could be deserialised with a missing field defaulting to zero" —
  REFUTED.** Neither `api/mod.rs:14-22` nor `transaction.rs:55-76` uses `#[serde(default)]`
  on any member; only `config.rs:25,28,53` do, and those are operator-side.
- **"An `else if` ordering bug in `decode_call` lets one selector shadow another" —
  REFUTED.** The eight arms at `target_effects.rs:71-129` dispatch on eight *distinct*
  4-byte selectors, and alloy's `abi_decode` checks the selector before the body, so arm
  order cannot matter. The one genuine collision is documented and deliberate:
  ERC-20 `approve(address,uint256)` and ERC-721 `approve(address,uint256)` share a
  selector (`target_effects.rs:29-31`), as do the two `setApprovalForAll`

- **"Checker-chain semantics let an error be mistaken for a verdict" — REFUTED at the
  engine layer.** `Checker::check` returns `Verdict` (not `Result`), and
  `engine/mod.rs:57-72` has no fallible step: the loop can only produce one of the three
  `Verdict` variants, defaulting to `Abstain` on an empty chain (`engine/mod.rs:62`).
  There is no path where an internal error is reported as `Secure`.
- **"`decode_multi_send` ignoring `allows_delegate_calls` is a bypass" — REFUTED.**
  `multi_send.rs:92-133` decodes `DelegateCall` sub-entries regardless of deployment, but
  it *returns* the flag to the caller (`multi_send.rs:164`), and `base.rs:210-212` is the

### My own leads

- **"`main.rs` builds the chain in an order that lets a later checker's `Insecure` be
  suppressed" — CONFIRMED as a fact but assigned to R9.** `main.rs:57-73` +
  `engine/mod.rs:62-69`. This is ENG-H1..H7's shared root cause and R9 owns
  `checkers/*`; filing it from `main.rs` would duplicate. Recorded as an observation.
- **"`RefundChecker`'s `chain_id = 0` bug has a sibling in `decode_multi_send`" —
  PARTIALLY CONFIRMED, recorded as an observation, not filed.** `multi_send.rs:116-129`
  builds every sub-transaction with `chain_id: U256::ZERO` and zeroed
  `safe_tx_gas`/`base_gas`/`gas_price`/`gas_token`/`refund_receiver`/`nonce` — the same
  shape as the `..Default::default` at `refund.rs:105-117` that ENG-H1 says makes the
  refund checker dead. Any consumer of `sub_transactions` (`cow.rs:429`,
  `staking.rs:93`) that reads one of those six fields on a sub-transaction silently reads
  zero. Today `cow.rs`/`staking.rs` read only `to`/`value`/`data`/`operation` on sub-calls
  and take `chain_id` from the top-level transaction, so nothing is wrong *yet*; but this
  is a loaded footgun in a decoder whose sibling has already fired once. It belongs to R9
  to confirm no sub-call consumer reads a zeroed field.
- **`Cursor::read` poisons itself on a failed read — REAL but with no impact today.**
  `multi_send.rs:182` does `mem::take(&mut self.0)` *before* `split_at_checked(len)?`, so
  when the read fails the `?` returns while `self.0` has already been replaced with the
  empty slice: the cursor silently becomes exhausted rather than staying put. Every
  current caller propagates the `None` straight out of `decode_multi_send`
  (`multi_send.rs:106-109`) and drops the cursor, so the poisoned state is never observed.
  A future caller that tried to recover from a failed read (peek, or "skip this entry")
  would silently see an empty rest-of-blob. Observation, not a finding — no reachable
  behaviour today.
- **"An attacker-supplied dynamic-array length in `abi_decode` pre-allocates" — could not
  be settled offline; observation, ~20%.** `erc1155::safeBatchTransferFromCall`
  (`bindings.rs:84`, decoded at `target_effects.rs:121-128`) has two `uint256[]`
  parameters, the classic shape for a decoder that does `Vec::with_capacity(len)` before
  bounds-checking `len`. alloy-sol-types 1.6.0 (`Cargo.lock:678-679`) is believed to
  bounds-check the sequence length against the remaining buffer, but **A6 applies: the
  source is not on disk and I did not execute anything**, so this is class `I` and below
  the 40% bar. Flagged for QA once a toolchain exists: one `#[test]` decoding
  `safeBatchTransferFrom` with an `ids` length word of `0xffffffff` and no body settles it.
- **`DEPLOYMENTS` covers MultiSend 1.3.0 / 1.4.1 / 1.5.0 only — observation, not filed.**
  The eight entries at `multi_send.rs:27-68` are two 1.5.0, two 1.4.1 and four 1.3.0
  (canonical + eip155, MultiSend + MultiSendCallOnly) — the same version floor as
  `base.rs:186-191`'s `CREATE_CALL_CONTRACTS`, which carries explicit
  `// 1.3.0 / 1.4.1 / 1.5.0` comments. A Safe still batching through a pre-1.3.0 MultiSend
  deployment therefore fails `known_deployment` (`multi_send.rs:73-78`), so
  `decode_multi_send_call` returns `None` (`multi_send.rs:152-155`) and `base.rs:206-208`
  denies it `Insecure R-4.2` — a *false denial of an honest batch*. I did not file this
  because I cannot verify offline either the canonical pre-1.3.0 addresses or whether
  Safenet's guard supports Safes of that vintage at all; asserting an address from memory
  would be exactly the hallucination the Critic exists to catch. Worth one lookup with
  network access.
- **`MultiSendVersion` per-deployment tagging (engine checklist item 6) — NOT VERIFIED,
  observation.** `multi_send.rs:111-114` rewrites `to == 0` to `safe` for the two
  `V150Plus` entries and leaves it as the zero address for the six `Legacy` ones; a
  mis-tagged deployment would be an R-4.1 bypass, since `base.rs:87-90` treats a call to
  the zero address as a call to "another contract" and allows it. Settling this needs
  Safe's `MultiSend.sol` per version, which is **not in this repo**
  (`contracts/src` has no Safe sources) and which I have no network to fetch. Class `I`;
  I decline to guess. This is the one item in my scope I could not discharge.
- **Dockerfile hardening — observation, deferred to R10.** `Dockerfile:16-28` has no
  `USER` directive, so the engine runs as root in the runtime image; there is also no
  `HEALTHCHECK` and no `EXPOSE`, and both base images float (`rust:1-slim`,
  `debian:trixie-slim`) although the build is `--locked` (`Dockerfile:11`). A
  `find . -name Dockerfile` + grep shows **none** of the four Dockerfiles in the repo sets
  `USER`, so this is a repo-wide pattern and belongs to R10's cross-cutting sweep, not to
  a `sentinel-engine`-only finding.
- **`panic = "abort"` would turn any reachable panic into a process kill — REFUTED.** The
  root `Cargo.toml` has no `[profile.release]` section at all, so unwinding is the
  default; `crates/sentinel-engine/Cargo.toml` sets no profile either. Combined with the
  panic census above (no reachable panic in scope), the "panic -> 500 -> missing vote"
  path in PROMPT §8 has no instance in my files. Note for the Critic: because
  `tower-http`'s `catch-panic` feature is **not** enabled (root `Cargo.toml:24` takes
  only `trace`), a panic anywhere in the checker chain would drop the connection rather
  than return a 500 — the sentinel would see a transport error, not a status code. That
  changes the shape of the symptom, not the presence of a defect.
- **"Missing auth / rate limiting on the engine API" — Informational by A3, NOT filed.**
  `api/mod.rs:25-31` adds no auth layer, which `docs/sentinel-engine.md` states as
  intentional ("The API currently specifies no authentication or rate limiting... Do not
  expose the reference API publicly without adding appropriate access controls at the
  deployment boundary"). I looked for a bypass *inside* the co-deployed boundary and found
  none: the only listener the engine opens is `TcpListener::bind(config.bind_address)`
  (`main.rs:75`) defaulting to `127.0.0.1:5473` (`config.rs:57-59`), plus the
  safenet-core metrics listener, and the sample config leaves `bind_address` commented out
  (`sentinel-engine.sample.toml:14-17`). Nothing in scope widens the bind address on its
  own. Per the launch brief, not inflated.
- **"`config.rs` accepts a dangerous default" — REFUTED for the fields that matter.**
  `rpc` and `engine.blocklist` and `engine.address_poisoning_lookback_blocks` are all
  **required** (no `#[serde(default)]`, `config.rs:23,39,42`), both tables are
  `deny_unknown_fields` (`config.rs:20,36`), `bind_address` defaults to loopback rather
  than `0.0.0.0` (`config.rs:57-59`), and `parses_sample_config` (`config.rs:146-153`)
  pins the shipped sample against the schema. The one real gap — no *cross-field*
  validation — is F-ENG-009.
- **"`sentinel-engine.sample.toml` drifts from the schema" — REFUTED.** Every key in the
  sample (`rpc`, `bind_address`, `engine.blocklist`,
  `engine.address_poisoning_lookback_blocks`, `engine.address_poisoning_max_block_range`,
  `observability.log_filter`, `observability.metrics_address`) exists in `config.rs:19-55`
  plus `safenet_core::observability::Config`, and `config.rs:146-153` is a test that
  actually loads the file from `CARGO_MANIFEST_DIR`. The sample contains no secrets — the
  only values are a public RPC URL and an empty blocklist.

## Observations (plausible, below the 40% bar — not findings)

1. **Failure-abstain vs policy-abstain are the same bytes** (`engine/mod.rs:46-47`), and
   the engine exports no verdict metric of its own, so a degraded RPC or CoW API silently
   converts the engine into "abstain everything" with only `warn!` lines to show for it.
   Mechanism lives in R9's and R7's files; ENG-H13.
2. **The whole `Insecure`-suppression class** (`main.rs:57-73` + `engine/mod.rs:62-69`):
   six checkers can affirm `Secure` and the first non-abstain wins, so every deny-only
   checker placed after an affirmer is unreachable for the shapes that affirmer accepts.
   ENG-H1..H7, R9's scope.
3. **`decode_multi_send` zeroes six of the twelve `SafeTransaction` fields on every
   sub-transaction** (`multi_send.rs:116-129`) — the same footgun that ENG-H1 says already
   fired in `refund.rs`. R9 should confirm no `sub_transactions` consumer reads one.
4. **`Cursor::read` leaves the cursor empty after a failed read** (`multi_send.rs:182`,
   `mem::take` before the fallible `split_at_checked`). No caller observes it today.
5. **Attacker-supplied `uint256[]` lengths in `safeBatchTransferFrom` decoding**
   (`bindings.rs:84` / `target_effects.rs:121-128`): allocation behaviour is
   alloy-internal and unverifiable offline (A6). ~20%. One decode test settles it.
6. **`multi_send.rs:27-68` covers only MultiSend 1.3.0+**; an honest batch through an older
   canonical deployment is denied `R-4.2` rather than allowed. Needs one address lookup.
7. **`MultiSendVersion` tagging is unverified** — Safe's `MultiSend.sol` is not in this
   repo, so I could not confirm that exactly the two `V150Plus` entries redirect
   `to == 0` to `address(this)`. Engine checklist item 6 remains open.
8. **The Dockerfile runs the engine as root** and both base images float; repo-wide, R10.
9. **`docs/sentinel-engine.md` omits the CoW API dependency** (ENG-H14). Reference-only
   material, so no finding; R10/documentation.
10. **Charter § 2.18 constrains the escape hatch to the Guard's own functions**
    ("Calls to the Safenet Guard's `announceTransaction` and `cancelAnnouncement`
    functions are auto-allowed by the Guard",
    `safenet-charter@44a1e53:Safenet_Arbitration_Charter.md:352`) while
    `checkers/escape_hatch.rs` affirms the shape for **any** `to`. This is ENG-H5 and
    `escape_hatch.rs` is R9's file — recorded here only so the Charter quote that settles
    it is on the record. § 2.18 line 354 also explicitly says the Guard does **not**
    constrain the announcement transaction's gas/refund parameters and that any
    `gasPrice == 0` requirement is "outside this Charter", which is relevant to how R9
    frames ENG-H4.
